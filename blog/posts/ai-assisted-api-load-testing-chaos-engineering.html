Chaos Testing and AI-Generated Load Scenarios for APIs

Jan 5, 2026 6 min read Sartaj Syed
Load Testing k6 Chaos Engineering

Writing load test scenarios by hand is tedious in a specific way: you have to read through an API's endpoints, guess at realistic payloads, decide on request patterns, and write scripts for all of it before you've run a single test. I built API Stress Lab to remove that first, tedious step. Upload an OpenAPI spec, and AI generates the test scenarios for you.

What the AI Actually Does

The tool takes an OpenAPI 3.x spec, JSON or YAML, and generates test scenarios from the endpoints and schemas it describes. It's worth being precise about what this means, because it's easy to overstate. The AI isn't simulating traffic or running the test. It's turning a spec into a plausible test plan, realistic payloads, sensible request sequences, so a person doesn't have to hand-write a script for every endpoint before testing anything. The actual load, the requests hitting the target API, runs through k6 underneath, which is a mature, purpose-built load-testing engine. AI replaces the scripting step, not the engine.

Beyond Clean Load: Chaos Testing

Running a system under clean, steadily increasing load tells you one thing. It doesn't tell you how the system behaves when things go wrong, which in production is most of what actually matters. The tool supports chaos testing on top of standard load profiles: deliberately injecting latency, simulating failures, forcing the kind of degraded conditions that are hard to reproduce on purpose otherwise. Seeing how a system degrades under partial failure is a different and arguably more useful signal than seeing how fast it responds when everything is healthy.

Turning Results Into Something Actionable

Raw load test output is a lot of numbers. The dashboard surfaces latency percentiles, p50, p95, p99, and RPS curves through Recharts, and pairs that with AI-generated analysis that flags likely bottlenecks and suggests fixes, rather than leaving someone to eyeball a chart and guess what's actually constraining the system.

Architecture

The frontend is Next.js 14 with Tailwind. The backend is FastAPI. Because a load test can run for a while and shouldn't block the request that started it, test execution happens asynchronously through Celery workers backed by a Redis queue. Postgres holds test configuration and results, and test artifacts live in MinIO or Cloudflare R2 depending on deployment.

Security Was Not Optional Here

A tool that takes a user-supplied API target and credentials and then generates traffic against it is a meaningfully different security surface than a typical CRUD app, and I treated it that way rather than as an afterthought. SSRF protection blocks requests to private IP ranges and cloud metadata endpoints specifically, since a load tester that will hit any URL you give it is a textbook SSRF vector if internal targets aren't explicitly blocked. Credentials are encrypted with Fernet, AES-128, rather than stored in plaintext. JWT authentication enforces per-user data isolation, so one user's test configurations and stored credentials are never visible to another user of the same instance.

What Building This Taught Me

The AI-assisted scenario generation genuinely cuts the time to a first useful test, that part of the pitch holds up. But the value of a tool like this still rests on the unglamorous parts: a real load-testing engine doing the actual work, async job handling that doesn't block on long-running tests, and security built with the assumption that it will eventually be pointed at real infrastructure with real credentials, not a demo environment. The AI layer is the part people notice first. It's not the part that makes the tool trustworthy to actually run against something that matters.
